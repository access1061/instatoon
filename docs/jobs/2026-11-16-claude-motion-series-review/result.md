# 원고 검토와 인스타툰 시리즈 방향안

2026-11-16. 현재 세션이 final/blog의 6편 원고와 final/review/REVIEW.md·VALIDATION.md, source/SERIES_GUIDE.md를 직접 읽고 검토했다. 코드 재실행·최신 공식 문서 검증·영상 청감 검수는 수행하지 않았다. 원본 자료는 수정하지 않았다.

## 권장 방향

가제: **AI랑 카드뉴스 만들다가 영상까지**

독자: AI로 콘텐츠를 만들고 싶지만 코드와 영상 제작이 낯선 사람.

중심 이야기: 붉은 머리 행동가가 “그림은 있는데 카드뉴스는 어떻게 만들지?”라고 묻는다. 은발 안내자가 기획과 제작 순서를 돕고, 보라 머리 분석가가 누락·오해를 짚는다. 정지 카드 완성에서 시작해 정보 전달용 모션을 붙이고 검수까지 끝내는 연속 사건이다.

6회 × 회당 4장, 총 24장을 권장한다. 회차마다 독립적으로 읽히며 다음 회차로 이어진다. 컬러 4:5, 최종 1080×1350. 장수와 제목은 이번 방향안의 제안이며 아직 확정되지 않았다. 한 장에는 큰 상황 하나와 짧은 말풍선 2~3개를 우선한다.

기본 진행 캐릭터는 판타지 3인 파티다. 치이카와는 기존 제작 예제의 소재이며, 진행 캐릭터로 채택한 것은 아니다. 실제 포스터·완성 카드·전후 비교는 필요할 때 화면 속 자료로 활용하되, 생성 이미지의 가짜 코드나 가짜 실행 화면을 실제 캡처로 소개하지 않는다.

## 원고 평가

재현용 예제, 기획표, 수정할 파일 위치, 실패한 렌더 경로까지 있어 시리즈의 재료는 충분하다. 특히 '막연한 요청 → 구체적 수정', '그림과 글자 분리', '파일 생성과 검수의 차이'는 인스타툰으로 옮기기 좋다.

다만 블로그 문단을 줄여 말풍선으로 옮기면 도구 이름과 명령어가 과밀해진다. 각 회차의 질문 하나와 실수 하나를 장면으로 만들고, 긴 코드와 설치 절차는 블로그 보충 자료로 연결하는 편이 적합하다. 게시 링크는 실제 URL을 받은 뒤 연결한다.

| 검토 지점 | 확인 내용과 편집 조치 |
| --- | --- |
| 초기안과 최종안 차이 | source 가이드는 16초·3.2초 기반의 초기 구성이다. final의 예제 결과인 정지 5장·24초를 기준으로 삼는다. 인스타툰 6회·24장과 별도로 설명한다. |
| 학습 순서 | final의 각 편 앞에 모션 추가 설명이 삽입되어 기본 절차를 끊는다. 입문→준비→기획→정지 카드→모션→검수로 다시 배열한다. |
| 준비물 축약 | '준비물 두 가지', 'doctor 한 번이면 끝'은 실제 실행 절차를 충분히 설명하지 못한다. 환경 점검·인증·실제 미리보기를 구분한다. |
| AI의 수행 범위 | 원고는 재현용 요청문임을 명시한다. 실제 대화 로그에 근거한 '당시 AI가 전부 완성했다'는 성공담으로 바꾸지 않는다. |
| 렌더 설명 | HyperFrames render는 해당 환경에서 미완료다. 최종 MP4는 HTML/GSAP→Edge 프레임 캡처→FFmpeg로 생성됐다는 구분을 유지한다. |
| 성능 수치 | 검수 문서의 실행 시간은 특정 PC의 측정값이다. '누구나 1분 만에 완성' 등의 홍보 문구로 일반화하지 않는다. |
| 음악 검수 | 오디오 스트림·파형 검사와 청감 검수는 다르다. 보고서는 청감 미수행을 명시한다. 음악까지 확인 완료로 쓰지 않는다. |
| 깨진 검수 기록 | REVIEW.md·VALIDATION.md의 모션 추가 부분은 물음표로 깨진 문장이 있다. 해당 부분의 문구를 증거로 재인용하지 않는다. |
| 행사 정보 | 제공 포스터 기반 예제다. 예약 정보 부재를 예약 불필요로 바꾸지 않는다. 최신 방문 안내로 재발행하려면 별도 확인이 필요하다. |
| 수정 위치 | build.py가 cards.json을 생성한다. 'JSON만 수정하면 된다'고 요약하면 변경이 사라질 수 있다. 원본 생성 스크립트 수정이라는 핵심을 유지한다. |

## 회차 구성

| 회차·가제 | 4장의 흐름 | 독자가 가져갈 한 가지 |
| --- | --- | --- |
| 1. 그림은 있는데 카드뉴스는 어떻게? | 결과를 보고 놀람 → 카드와 영상 규격 비교 → Claude Code·웹 기술·인코딩의 역할 → 만들 결과부터 정하기 | 도구를 켜기 전에 출력 목표를 정한다. |
| 2. 설치했는데 왜 안 되지? | 설치 후 막힘 → 작업 폴더와 터미널 구분 → doctor·lint·미리보기의 역할 → 오류 난 단계부터 확인 | 설치와 작동 확인은 각각 필요하다. |
| 3. '예쁘게' 말고 무엇을 부탁할까? | 막연한 요청으로 정보 누락 → 확인된 정보와 미확인 정보 분리 → 카드마다 질문 하나 → 자료·장별 역할·규격을 적은 요청 | 무엇을 전달할지 정해야 요청도 구체적이 된다. |
| 4. 날짜 하나 바꾸는데 다시 그려? | 글자 오류 발견 → 그림과 HTML 글자 레이어 분리 → 대상을 좁힌 수정 요청 → PNG 크기·가독성 확인 | 수정할 부분을 분리하면 다음 제작에도 활용하기 쉽다. |
| 5. 다 움직이면 더 잘 보일까? | 모든 요소를 흔들어 혼란 → 날짜·장소·체크의 읽는 순서 → 원본 그림과 별도 모션 레이어 비교 → 읽을 시간과 출력 확인 | 움직임은 정보의 순서를 돕도록 배정한다. |
| 6. 파일이 나왔다고 완성은 아님 | 출력 성공에 환호 → 날짜·글자·음악 누락 발견 → 확인 목록과 실제 렌더 경로 기록 → 새 자료로 재사용 | 출력·내용·재생을 각각 확인한다. |

각 회차 마지막은 다음 편 예고를 길게 붙이지 않고 질문 한 줄로 연결한다. 예: 1회 끝 '그럼, 어디서 실행해?' → 2회 시작의 설치 문제.

## 1회 4장 원고 샘플

창작 대사 초안이며 실제 대화 인용이 아니다. 화면의 정보 카드와 말풍선은 분리한다.

| 장 역할 | 핵심 의미 | 캐릭터 행동 | 정확한 문구 초안 |
| --- | --- | --- | --- |
| 질문 | 자료는 있지만 시작이 막막함 | 행동가가 그림 파일을 들고 빈 캔버스 앞에서 멈춤 | 행동가: “그림은 있는데…” / 행동가: “카드뉴스는 어떻게 만들지?” |
| 목표 | 정지 카드와 영상의 결과 구분 | 안내자가 카드 묶음과 세로 영상 화면을 나란히 펼침 | 안내자: “먼저 결과부터 정하자.” / 정보 카드: “정지 카드 5장” “24초 세로 영상” |
| 역할 | 제작 요청과 구현 과정 이해 | 세 사람이 요청서→카드 화면→영상 파일을 연결함 | 행동가: “AI가 영상도 바로 줘?” / 안내자: “화면과 움직임을 코드로 만들고,” / 분석가: “실행해서 파일로 내보내.” |
| 행동 | 구체적 출력 목표부터 시작 | 행동가가 요청서에 결과 규격을 적음 | 행동가: “그럼 첫 요청은?” / 안내자: “무엇을 몇 장 만들지부터!” / 정보 카드: “정지 1080×1350 / 영상 1080×1920” |

마지막 정보 카드는 글자 크기가 작아지면 캡션으로 옮긴다. GSAP·HyperFrames·FFmpeg의 세부 역할은 1회 캡션과 후속 회차에서 풀어낸다. 한 장 안에 도구 이름을 모두 나열하지 않는다.

## 제작 전 반영 기준

- 최신 명령이나 설치 버전을 싣는 경우 해당 공식 문서를 다시 확인한다. 이번 검토는 로컬 원고의 편집 검토다.
- 첫 회차 이미지가 안정되면 실제 생성본을 이후 장의 스타일 앵커로 사용한다.
- 각 장은 실제 이미지 생성→Paseo Visual QA→필요 시 수정 순으로 진행한다. 정확한 크기 보정 후 완성 이미지에 맞춰 회차별 100~500자 캡션을 작성한다.
- 이번 단계에서는 이미지와 게시 캡션을 생성하지 않았다.
